# backend

Minimal [ElysiaJS](https://elysiajs.com/) + [Bun](https://bun.sh/) API with async task processing, WebSocket updates, Swagger UI, and an optional Redis cache.

## Requirements

- Bun 1.4+

## Setup

```bash
bun install
cp .env.example .env
bun run dev
```

Bun loads `.env` automatically. The server listens on `http://localhost:3000` by default.

### Environment

| Variable    | Default | Description                                                                 |
| ----------- | ------- | --------------------------------------------------------------------------- |
| `PORT`      | `3000`  | HTTP port.                                                                  |
| `REDIS_URL` | empty   | Optional Redis/Valkey URL for cache and task snapshots. Empty means memory. |

Example:

```dotenv
PORT=3000
REDIS_URL=redis://localhost:6379
```

If `REDIS_URL` is set but Redis cannot be reached at startup, the app logs a warning and falls back to in-memory storage instead of refusing to boot. If Redis goes away later, task snapshots fall back to memory and the app keeps running.

## Endpoints

```bash
curl http://localhost:3000/
# {"message":"Hello World"}

curl http://localhost:3000/health
# {"status":"ok","cache":"memory","tasks":"memory"}

curl -i http://localhost:3000/cached
# x-cache: MISS (memory)
# {"message":"Hello World","generatedAt":"..."}

curl -i http://localhost:3000/cached
# x-cache: HIT (memory)
# {"message":"Hello World","generatedAt":"..."}
```

`/cached` is a small cache demo: the value is stored for 10 seconds, and the `x-cache` header shows whether it came from the cache.

## API documentation

- Swagger UI: `http://localhost:3000/docs`
- OpenAPI JSON: `http://localhost:3000/docs/json`

Generated by [`@elysia/openapi`](https://www.npmjs.com/package/@elysia/openapi) from the Elysia route schemas and `detail` metadata. Request bodies, parameters, and success responses are documented. WebSocket updates are not part of OpenAPI, so they are described below.

## Task processing

All processing endpoints return `202 Accepted` immediately with a task ID:

| Endpoint            | Body                    |
| ------------------- | ----------------------- |
| `POST /process/text`  | `{"text":"..."}`      |
| `POST /process/image` | `{"url":"https://..."}` |
| `POST /process/video` | `{"url":"https://..."}` |
| `POST /process/url`   | `{"url":"https://..."}` |

```bash
curl -X POST http://localhost:3000/process/text \
  -H 'content-type: application/json' \
  -d '{"text":"Hello from a background task"}'
# {"taskId":"...","status":"queued"}
```

```bash
curl http://localhost:3000/tasks/<taskId>
# {"id":"...","kind":"text","status":"completed","progress":100,...}
```

Tasks run in-process and always have an in-memory copy for fast access. When Redis was available at startup, snapshots are also written through to Redis with a one-hour TTL, so `GET /tasks/:id` and WebSocket subscriptions can recover a task after a restart or from another instance. If Redis becomes unavailable, task persistence drops back to memory. The actual processing is still in-process, so a task that was mid-flight during a restart is not resumed; a durable queue (for example BullMQ + Redis) would be the next step.

## WebSocket updates

Elysia has built-in WebSocket support through Bun. Connect to `ws://localhost:3000/ws`.

Client actions:

```json
{"action":"subscribe","taskId":"<uuid>"}
{"action":"unsubscribe","taskId":"<uuid>"}
```

Server events always use a `{ type, data }` envelope:

```ts
type ServerEvent =
  | { type: "connected"; data: { message: string } }
  | { type: "subscribed"; data: { taskId: string; topic: string } }
  | { type: "unsubscribed"; data: { taskId: string; topic: string } }
  | { type: "task.snapshot"; data: { task: Task } }
  | { type: "task.update"; data: { task: Task } }
  | { type: "task.completed"; data: { taskId: string; result: unknown; completedAt: string } }
  | { type: "task.failed"; data: { taskId: string; error: string; failedAt: string } }
  | { type: "error"; data: { code: "invalid_action" | "task_not_found"; message: string } };
```

`task.completed` and `task.failed` are explicit terminal events. A late subscriber gets the current `task.snapshot` plus the terminal event if the task already finished. Intermediate progress arrives as `task.update`.

Minimal client:

```js
const response = await fetch("http://localhost:3000/process/text", {
  method: "POST",
  headers: { "content-type": "application/json" },
  body: JSON.stringify({ text: "Hello" }),
});
const { taskId } = await response.json();

const ws = new WebSocket("ws://localhost:3000/ws");
ws.onopen = () => ws.send(JSON.stringify({ action: "subscribe", taskId }));
ws.onmessage = (event) => {
  const message = JSON.parse(event.data);
  console.log(message);

  if (message.type === "task.completed") {
    console.log("Finished:", message.data.result);
    ws.send(JSON.stringify({ action: "unsubscribe", taskId }));
  }
};
```

The protocol types live in `src/tasks/protocol.ts`.

## Cache

The cache is provided by [`@clov-std/kv-store`](https://www.npmjs.com/package/@clov-std/kv-store), which uses Bun's native Redis client. It is exposed to route handlers as `cache`:

```ts
.get("/example", async ({ cache }) => {
  const value = await cache.get<string>("key");
  await cache.set("key", "value", 60); // TTL in seconds
  return { value };
});
```

## Docker

```bash
docker build -t backend .
docker run --rm -p 3000:3000 backend
```

To use Redis, pass the URL at runtime (the `.env` file is not baked into the image):

```bash
docker run --rm -p 3000:3000 \
  -e REDIS_URL=redis://host.docker.internal:6379 \
  backend
```

Set `PORT` too if you want the container to listen somewhere other than `3000`.
